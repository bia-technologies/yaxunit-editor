## Общая архитектура

Парсер построен на базе библиотеки Chevrotain и состоит из следующих основных компонентов:

1. **Токенизатор (Lexer)** - разбивает исходный текст на токены
2. **Парсер (Parser)** - строит дерево разбора (CST) согласно грамматике языка
3. **Инкрементальный парсер** - поддерживает обновление только изменённых частей кода
4. **Посетитель (Visitor)** - преобразует CST в семантическую модель кода

```
Исходный текст → Lexer → Токены → Parser → CST → Visitor → Семантическая модель
```

## Структура файлов

- **tokens.ts** - определения токенов и ключевых слов языка
- **lexer.ts** - токенизация и инкрементальное обновление токенов
- **parser.ts** - грамматика языка BSL, построение CST
- **incrementalBslParser.ts** - инкрементальный парсер с поддержкой частичных обновлений
- **visitor.ts** - базовый посетитель для обхода CST
- **index.ts** - экспорты модуля

## Токенизация (tokens.ts, lexer.ts)

### Определение токенов

Токены определены в `tokens.ts` с использованием Chevrotain API:

- **Идентификаторы**: `Identifier` - слова, начинающиеся с буквы/подчёркивания
- **Ключевые слова**: определяются через функцию `keyword()` с поддержкой кириллицы
- **Операторы**: сгруппированы по категориям (AdditionOperator, MultiplicationOperator, CompareOperator)
- **Литералы**: числа, строки, даты, булевы значения
- **Специальные символы**: скобки, точки, запятые и т.д.

Особенности:
- Поддержка кириллических ключевых слов (русский язык)
- Ключевые слова используют `longer_alt: Identifier` для корректного приоритета
- Строки поддерживают многострочный формат с переносами

### Инкрементальная токенизация

`IncrementLexer` наследуется от стандартного `Lexer` Chevrotain и добавляет:

- **`moduleTokens`** - массив всех токенов модуля (сохраняется между обновлениями)
- **`updateTokens(changes)`** - обновляет только затронутые токены

#### Алгоритм обновления токенов

1. Для каждого изменения определяется диапазон токенов, который затрагивается
2. Функция `findTokens()` находит границы затронутых токенов (бинарный поиск)
3. Если изменение попадает внутрь токена, токен пересобирается из частей:
   - Левая часть старого токена + новый текст + правая часть старого токена
4. Новые токены вставляются в массив, старые удаляются
5. Смещения (`startOffset`, `endOffset`) всех последующих токенов корректируются

**Важно**: алгоритм учитывает границы токенов и может частично пересобрать токены, которые пересекаются с областью изменения.

## Парсер (parser.ts)

### Базовая структура

`BSLParser` наследуется от `CstParser` (Chevrotain) и определяет грамматику языка BSL.

Настройки парсера:
- `nodeLocationTracking: "onlyOffset"` - отслеживание только смещений узлов (экономия памяти)
- `recoveryEnabled: true` - включено восстановление после ошибок

### Структура грамматики

Грамматика организована в три основных раздела:

#### 1. Модуль и определения (definitions)

- **`module`** - корневое правило: последовательность процедур, функций и операторов верхнего уровня
- **`procedure`** - объявление процедуры:
  ```
  [Async] Procedure Имя(параметры) [Export]
      операторы
  EndProcedure
  ```
- **`function`** - объявление функции (аналогично процедуре, но с `EndFunction`)
- **`parameter`** - параметр: `[Val] Имя [= значение_по_умолчанию]`

#### 2. Операторы (statements)

Правило `statements` использует `MANY()` для последовательности операторов, разделённых точкой с запятой.

Список операторов (массив `statement`):
- **Конструкторы** (`constructors()`) - три варианта конструктора `New`
- **`returnStatement`** - `Return [выражение]`
- **`tryStatement`** - блок Try/Except/EndTry
- **`riseErrorStatement`** - `Raise выражение`
- **`varStatement`** - `Var переменная1, переменная2, ...`
- **`ifStatement`** - `If ... Then ... [Elsif ... Then ...]* [Else ...] EndIf`
- **`whileStatement`** - `While условие Do ... EndDo`
- **`forStatement`** - `For переменная = начало To конец Do ... EndDo`
- **`forEachStatement`** - `For Each переменная In коллекция Do ... EndDo`
- **`continueStatement`**, **`breakStatement`** - управление циклом
- **`gotoStatement`** - `Goto ~метка`
- **`labelStatement`** - `~метка:`
- **`addHandlerStatement`**, **`removeHandlerStatement`** - работа с обработчиками событий
- **`preprocessor`** - директивы препроцессора (#Region, #If и т.д.)
- **`awaitStatement`** - `Await выражение`
- **`executeStatement`** - `Execute выражение`
- **`assignmentStatement`** - присваивание или вызов метода
- **`EMPTY_ALT`** - пустая альтернатива (для необязательных элементов)

#### 3. Выражения (expressions)

Выражения построены с использованием приоритетов операторов через цепочку правил:

```
expression
  → logicalOrExpression
    → logicalAndExpression
      → compareExpression
        → additionExpression
          → multiplicationExpression
            → operand
```

**Операнды (`operand`)**:
- Унарные операторы: `Not`, `-`, `+` (опционально)
- Тернарный оператор: `?(условие, значение1, значение2)`
- Литералы: числа, строки, даты, булевы значения, `Undefined`, `Null`
- Квалифицированное имя: `qualifiedName`
- Скобки: `(выражение)`

**Квалифицированное имя (`qualifiedName`)**:
- Начинается с идентификатора или вызова метода
- Далее может следовать цепочка:
  - `.метод(аргументы)` - вызов метода
  - `.поле` - доступ к полю
  - `[индекс]` - доступ по индексу
- Поддерживается незавершённое имя (точка в конце) для автодополнения

**Методы вызова**:
- **`methodCall`** - имя метода, затем аргументы в скобках
- **`methodCall2`** - аналогично, но первым токеном может быть `Execute` (для вызова по строке)
- **`arguments`** - список аргументов: `(выражение1, выражение2, ...)`
- **`argument`** - отдельный аргумент (может быть пустым)

**Конструкторы**:
- **`constructorExpression`** - `New Тип([аргументы])`
- **`constructorMethodExpression`** - `New(тип[, аргументы])`
- **`constructorBad`** - `New` без аргументов (обработка ошибки)

### Вспомогательные методы

- **`binaryExpression(operand, operator)`** - генерирует правило для бинарного оператора:
  ```
  операнд (оператор операнд)*
  ```
  Используется для операторов с левой ассоциативностью

- **`choice(...tokens)`**, **`choice1(...tokens)`** - обёртки для `OR()` с разными индексами (для разрешения конфликтов)

## Инкрементальный парсер (incrementalBslParser.ts)

`IncrementalBslParser` расширяет `BSLParser` и добавляет поддержку инкрементального парсинга.

### Основные методы

#### `parseModule(text: string)`

Полный парсинг модуля:
1. Токенизация всего текста через `lexer.tokenize()`
2. Сохранение токенов в `lexer.moduleTokens`
3. Парсинг через правило `module()`
4. Возврат результата: `{ cst, lexErrors, parseErrors }`

#### `updateTokens(changes: IModelContentChange[])`

Обновление токенов при изменении текста:
- Делегирует работу инкрементальному лексеру
- Возвращает массив диапазонов с информацией об изменениях

#### `parseChanges(rule: string, startOffset: number, endOffset: number)`

Парсинг только изменённого фрагмента:
1. Находит границы токенов через `findSymbolTokens()`
2. Вырезает нужный диапазон токенов
3. Вызывает указанное правило парсера (например, `statements`, `expression`)
4. Возвращает результат парсинга

**Важно**: используется для инкрементального обновления модели кода - перепарсивается только изменённая область.

### Вспомогательные функции

**`findSymbolTokens(tokens, startOffset, endOffset)`**:
- Бинарный поиск токенов, пересекающихся с диапазоном
- Возвращает `{ startIndex, endIndex, includeStart, includeEnd }`
- Используется для определения, какие токены нужно перепарсить

## Посетитель (visitor.ts)

`BslVisitor` - базовый класс для обхода CST и преобразования его в семантическую модель.

Наследуется от `BaseVisitor`, сгенерированного Chevrotain на основе грамматики.

### Основные методы

- **`visit(cstNode)`** - обход узла или массива узлов
- **`visitAll(nodes)`** - обход массива узлов, возвращает массив результатов
- **`visitFirst(cstNode)`** - обход первого элемента массива (опционально)

### Вспомогательные статические методы

- **`firstToken(ctx)`** - извлекает первый токен из контекста
- **`firstNode(ctx)`** - извлекает первый узел из контекста

**Примечание**: конкретная реализация преобразования CST в модель кода находится в `codeModelFactoryVisitor.ts`, который наследуется от `BslVisitor`.

## Важные детали реализации

### Приоритет операторов

Приоритет задаётся через цепочку правил:
```
logicalOrExpression (Or)
  → logicalAndExpression (And)
    → compareExpression (=, <>, <, <=, >, >=)
      → additionExpression (+, -)
        → multiplicationExpression (*, /, %)
          → operand (унарные операторы, литералы, имена)
```

### Обработка ошибок

Парсер использует встроенное восстановление Chevrotain (`recoveryEnabled: true`), что позволяет продолжать парсинг при обнаружении синтаксических ошибок.

Ошибки разделяются на:
- **Лексические** (`lexErrors`) - ошибки токенизации
- **Синтаксические** (`parseErrors`) - ошибки грамматики

### Метки (LABEL)

В правилах используются метки для явного именования узлов в CST:
```typescript
this.CONSUME(tokens.Identifier, { LABEL: 'name' })
this.SUBRULE(this.expression, { LABEL: 'condition' })
```

Это упрощает доступ к конкретным элементам в visitor'е.

### Незавершённые конструкции

Парсер поддерживает незавершённые конструкции для автодополнения:
- Незавершённое квалифицированное имя (точка в конце)
- Пустые аргументы в вызовах методов
- Незавершённые строки (`UnclosingString`)

### Индексы правил (OR1, OR2, CONSUME1, CONSUME2)

В некоторых правилах используются пронумерованные варианты (`OR1`, `CONSUME1` и т.д.) для разрешения конфликтов в грамматике Chevrotain, когда один и тот же токен может встречаться в разных контекстах.

## Работа с кодом

### Добавление нового оператора

1. Добавить правило в `parser.ts` в секцию statements
2. Добавить правило в массив `statement`
3. Реализовать обработку в `codeModelFactoryVisitor.ts`

### Добавление нового выражения

1. Определить правило в секции expressions
2. Добавить в цепочку приоритетов (если это оператор)
3. Обновить visitor для обработки нового узла

### Добавление нового токена

1. Добавить определение в `tokens.ts`
2. Если это ключевое слово - использовать функцию `keyword()`
3. Обновить грамматику для использования нового токена

### Отладка парсера

- Использовать `console.log` для вывода промежуточных результатов
- Проверять структуру CST через visitor
- Смотреть ошибки парсинга в `parseErrors`
- Использовать playground для тестирования на реальных примерах

## Примеры грамматики

### Пример 1: Простая процедура

```bsl
Процедура Тест()
    Возврат;
КонецПроцедуры
```

Структура CST:
```
module
  └─ procedure
      ├─ name: Identifier("Тест")
      ├─ parameter: (пусто)
      └─ statements
          └─ returnStatement
              └─ (без выражения)
```

### Пример 2: Условие с выражением

```bsl
Если а > 0 Тогда
    б = 10;
КонецЕсли
```

Структура CST:
```
ifStatement
  └─ branch (ifBranch)
      ├─ condition: expression
      │   └─ compareExpression
      │       ├─ lhs: qualifiedName("а")
      │       ├─ operator: Greater
      │       └─ rhs: literal(Number("0"))
      └─ body: statements
          └─ assignmentStatement
              ├─ qualifiedName("б")
              └─ expression: literal(Number("10"))
```

### Пример 3: Вызов метода с цепочкой

```bsl
Объект.Метод1().Поле.Метод2(Аргумент1, Аргумент2)[Индекс]
```

Структура CST:
```
qualifiedName
  ├─ methodCall
  │   ├─ Identifier("Объект")
  │   └─ arguments (Метод1)
  ├─ methodCall (метод2)
  │   ├─ Identifier("Метод2")
  │   └─ arguments (Аргумент1, Аргумент2)
  ├─ Identifier("Поле")
  └─ indexAccess
      └─ expression: Identifier("Индекс")
```

## Практические советы

### Добавление нового оператора

**Шаг 1**: Определить правило в `parser.ts`

```typescript
protected newStatement = this.RULE("newStatement", () => {
    this.CONSUME(tokens.NewKeyword)
    this.SUBRULE(this.expression)
})
```

**Шаг 2**: Добавить в массив `statement`

```typescript
protected statement = [
    // ...
    () => this.SUBRULE(this.newStatement),
    // ...
]
```

**Шаг 3**: Реализовать visitor в `codeModelFactoryVisitor.ts`

```typescript
newStatement(ctx: CstChildrenDictionary) {
    return new NewStatementSymbol(
        this.visit(ctx.expression[0])
    )
}
```

### Отладка парсинга

**Проверка токенов:**
```typescript
const parser = new IncrementalBslParser()
const result = parser.parseModule(text)
console.log('Tokens:', parser.lexer.moduleTokens)
console.log('Lex errors:', result.lexErrors)
console.log('Parse errors:', result.parseErrors)
```

**Визуализация CST:**
```typescript

```

**Проверка конкретного правила:**
```typescript
parser.input = parser.lexer.moduleTokens

```

### Частые проблемы

**1. Конфликт токенов (ambiguous)**

Проблема: Chevrotain не может определить, какой токен использовать.

Решение:
- Использовать пронумерованные варианты (`OR1`, `CONSUME1`) для разрешения конфликтов
- Переупорядочить правила для изменения приоритета
- Использовать `longer_alt` для ключевых слов

**2. Незавершённые конструкции не парсятся**

Проблема: Парсер ожидает закрывающий токен, но его нет.

Решение:
- Убедиться, что правила используют `OPTION()` для необязательных элементов
- Добавить `EMPTY_ALT` где необходимо
- Проверить, что recovery enabled (`recoveryEnabled: true`)

**3. Инкрементальное обновление не работает**

Проблема: `updateTokens()` не находит правильные границы.

Решение:
- Проверить, что `startOffset` и `endOffset` корректны
- Убедиться, что токены отсортированы по offset
- Проверить логику в `findTokens()` и `findSymbolTokens()`

**4. Visitor не вызывается для узла**

Проблема: Метод visitor не найден для правила.

Решение:
- Имя метода должно точно совпадать с именем правила (camelCase)
- Проверить, что правило действительно создаёт узел (не пропущено)
- Использовать `this.validateVisitor()` для проверки

### Оптимизация производительности

1. **Использовать инкрементальный парсинг** для частых небольших изменений
2. **Ограничить отслеживание позиций** - `nodeLocationTracking: "onlyOffset"` вместо `"full"`
3. **Кэшировать парсер** - не создавать новый экземпляр для каждого парсинга
4. **Избегать глубокой рекурсии** - использовать итеративные подходы где возможно

## Связь с остальным кодом

Парсер используется в:
- **`codeModelFactory.ts`** - фабрика для построения семантической модели
- **`codeModelFactoryVisitor.ts`** - преобразование CST в модель кода
- **`moduleModel.ts`** - интеграция с Monaco Editor

Процесс работы:
```
Текст → IncrementalBslParser.parseModule() 
     → CST 
     → CodeModelFactoryVisitor.visit() 
     → BslCodeModel (семантическая модель)
```

## Диаграмма приоритетов операторов

```
Приоритет (от низкого к высокому):
┌─────────────────────────────────────┐
│ logicalOrExpression                 │  Or (или)
│   └─ logicalAndExpression           │  And (и)
│       └─ compareExpression          │  =, <>, <, <=, >, >=
│           └─ additionExpression     │  +, -
│               └─ multiplicationExpr │  *, /, %
│                   └─ operand        │  унарные: Not, -, +
│                                     │  операнды: литералы, имена, скобки
└─────────────────────────────────────┘
```

**Пример разбора:**
```
а + б * в И г > 0
```

Разбор по приоритетам:
1. `б * в` (multiplication) - самый высокий приоритет
2. `а + (б * в)` (addition)
3. `г > 0` (compare)
4. `(а + (б * в)) И (г > 0)` (logicalAnd)

## Заметки для разработчиков

### Архитектурные решения

1. **Инкрементальный парсинг**: Реализован для оптимизации обновления модели при редактировании кода. Перепарсивается только изменённая область.

2. **Только смещения (onlyOffset)**: Отслеживаются только начальные и конечные смещения узлов, не полная информация о строках/столбцах. Это экономит память.

3. **Восстановление после ошибок**: Включено по умолчанию, позволяет парсеру продолжать работу даже при синтаксических ошибках.

4. **Метки (LABEL)**: Используются для явного именования узлов в CST, что упрощает доступ в visitor'е.

### Возможные улучшения

1. **Кэширование парсера**: Текущая реализация создаёт новый парсер. Можно переиспользовать экземпляр.

2. **Улучшение ошибок**: Более информативные сообщения об ошибках с указанием ожидаемых токенов.

3. **Поддержка синтаксического сахара**: Расширение грамматики для поддержки дополнительных конструкций языка.

4. **Профилирование**: Добавление более детального профилирования для оптимизации горячих мест.

5. **Валидация грамматики**: Автоматические тесты для проверки покрытия всех правил грамматики.
